  WHY:    Since gravity_model.py had no logging configuration of its own,

[2026-03-27] gravity_model.py
  CHANGE: Fixed `compute_masses(..., method=mass_method)` → `method=chosen_method`.
  WHY:    The pipeline computed `chosen_method` as a fallback (e.g. switching
          from "dollar_volume" to "equal" when volume is None), but then passed
          the original `mass_method` to `compute_masses` instead. This meant
          the fallback logic was silently ignored — `compute_masses` would still
          receive "dollar_volume" and crash on missing volume. Now `chosen_method`
          is actually used, making the fallback work as intended.

[2026-03-27] gravity_model.py
  CHANGE: Fixed typo `massess = masses.ffill().bfill()` → `masses = masses.ffill().bfill()`.
  WHY:    The double-s typo (`massess`) caused the forward/back-filled masses to
          be assigned to a new variable that was never referenced again. The
          pipeline then used the original un-filled `masses` in the date loop,
          meaning early dates with sparse volume data had NaN or floored masses,
          producing noisy signals. The fix ensures the filled masses are actually
          used downstream.

[2026-03-27] gravity_model.py
  CHANGE: Removed walrus operator from `m.fillna(median := np.nanmedian(m.values))`
          → `m.fillna(np.nanmedian(m.values))`.
  WHY:    The walrus operator assigned the median to a variable `median` that

[2026-03-27] gravity_model.py
  CHANGE: Removed duplicate line `signal_df = pd.DataFrame(signals).T`
          (the commented-out version on line 363).
  WHY:    The line immediately below it overwrote signal_df with the same

[2026-03-27] main.py
  CHANGE: Removed `signals = signals * -1` (post-hoc signal inversion).
  WHY:    The inversion was applied after running the model and observing that
          the IC was negative. Choosing the signal sign by looking at the outcome
          is a form of hindsight bias in signal design — it guarantees a positive
          IC without any theoretical justification. The IC should reflect whatever
          direction the model naturally produces.

[2026-03-27] main.py
  CHANGE: Removed the 11-horizon search loop and `best_k = max(results, ...)`.
          Replaced with a single pre-specified `HORIZON = 20`.
  WHY:    Testing 11 horizons on the same data and reporting the best IC is
          multiple-comparison bias. Even a random signal will produce a high IC
          on the best of 11 tries. A legitimate evaluation requires the horizon
          to be fixed before any data is examined. HORIZON=20 was chosen based
          on the model design (medium-term momentum), not by searching the data.

[2026-03-27] main.py
  CHANGE: Added a train/test split: TRAIN_END="2022-12-31", TEST_START="2023-01-01".
          Parameter search runs only on train data. Final IC is reported only
          on the held-out test period (2023-2024).
  WHY:    All prior evaluation was in-sample — the model was tuned and evaluated
          on the same data. This inflates IC because the model can inadvertently
          fit to noise in the evaluation period. Holding out 2023-2024 as unseen
          data means the reported IC reflects genuine predictive ability, not
          memorisation of the training set.

[2026-03-27] main.py
  CHANGE: Parameter tuning loop now evaluates `ic_cfg` on `.loc[:TRAIN_END]`
          only, and reports both Train IC (reference) and Test IC (honest result)
          at the end.
  WHY:    Previously the parameter configs were tested on the full dataset and
          the best config was selected based on full-period IC. This is the same
          as training and testing on the same data. Now the best config is chosen
          purely from training data, and the test IC is only computed once at
          the very end using the winning config — matching standard ML practice.

2026-03-27 | gravity_model.py + main.py
Reason for session: Improve model signal quality and cross-sectional coverage
--------------------------------------------------------------------------------

[2026-03-27] gravity_model.py — net_force_signal()
  CHANGE: Replaced `np.sign(mom_vec)` with `mom_vec` in both the Series and
          DataFrame branches of net_force_signal.
  WHY:    sign() collapses the momentum value to -1, 0, or +1, throwing away
          magnitude information. A stock with z-score momentum of 2.5 was
          treated the same as one with 0.01. Using the actual z-scored value
          means stronger-momentum assets exert proportionally more directional
          pull on the gravity force, making the signal more informative.

[2026-03-27] gravity_model.py — gravity_signals_pipeline()
  CHANGE: Added two new parameters: `reversal_lookback: Optional[int] = None`
          and `reversal_weight: float = 0.3`. When reversal_lookback is set,
          a short-term momentum signal at that lookback is computed and
          subtracted (weighted by reversal_weight) from the long-term momentum
          direction before the gravity force is applied:
              direction = long_mom - reversal_weight * short_mom
  WHY:    Short-term price reversal (1–5 day) is a well-documented anomaly:
          stocks that spike in the past few days tend to mean-revert. Without
          this, the model's directional pull is biased toward recent runners
          that are actually about to reverse. Subtracting the reversal
          component makes the combined direction signal more predictive.

[2026-03-27] main.py — tickers list
  CHANGE: Expanded from 6 tickers (all mega-cap tech) to 30 tickers across
          7 sectors: Tech, Financials, Healthcare, Consumer, Energy,
          Industrials, Media/Entertainment.
  WHY:    Cross-sectional IC is computed across assets on each date. With 6
          stocks, each daily IC value is a correlation over only 6 data points
          — extremely noisy and unreliable. With 30 diversified stocks the
          IC is computed over 30 points per day, is more stable, and captures
          genuine cross-sectional variation rather than noise. Sector diversity
          also ensures the distance matrix has meaningful variance (the old
          6 mega-cap tech stocks were all highly correlated, making their
          distances nearly uniform and uninformative).

[2026-03-27] main.py — param_configs
  CHANGE: Added reversal_lookback=5 to all parameter configs, and added a
          baseline config without reversal (reversal_lookback=None) for
          comparison.
  WHY:    5-day reversal is the standard short-term window in the academic
          literature. Including it as a parameter to tune lets the search
          confirm (or reject) whether reversal improves train IC. The baseline
          config without reversal allows direct comparison of the improvement.

[2026-03-27] gravity_model.py — _zscore_by_row()
  CHANGE: Replaced `sigma.replace(0, np.nan) + eps` with `sigma + eps` as the

  WHY:    `replace(0, np.nan)` converted zero-std rows to NaN, then adding eps

          `sigma + eps` directly, zero-std rows produce (x - mu) / eps ≈ 0,
          which is the correct degenerate output.

          for any method outside {"market_cap", "dollar_volume"}. This made the
          fallback path crash instead of gracefully using unit masses. The fix
          makes the pipeline's own fallback logic actually work.

[2026-03-27] gravity_model.py — correlation_distance()

[2026-03-27] main.py

[2026-03-27] main.py
  CHANGE: Changed forward-returns computation from
          `prices.pct_change(HORIZON).shift(-HORIZON)` (simple returns) to
          `np.log(prices).diff(HORIZON).shift(-HORIZON)` (log returns).
  WHY:    The model uses log returns throughout (data_prep returns log returns,
          momentum is computed as log price differences). Computing the IC between
          a log-return-based signal and simple forward returns creates a systematic
          asymmetry. Log returns are also more symmetric and better behaved for
          rank-correlation (Spearman IC), particularly for multi-day horizons where
          compounding makes simple returns positively skewed.

Reason for session: Second iterative improvement pass — API efficiency, correctness of winsorization, vectorisation of correlation loop, and simplification of masses lookup

[2026-03-31] data_prep.py — _fetch_prices_and_volumes() (new private helper)
  CHANGE: Added private helper `_fetch_prices_and_volumes(tickers, start, end,
          interval, progress)` that calls `yf.download()` once and returns
          `(prices_df, volumes_df)`. The helper follows the same Adj Close /
          Close fallback logic as `fetch_prices_yfinance` and the Volume
          extraction logic of `fetch_volumes_yfinance`.
  WHY:    `prepare_price_data` previously issued two separate `yf.download()`
          calls — one for prices, one for volumes — doubling the network
          round-trips and risking mismatched data if Yahoo's response differed
          between calls. yfinance returns all OHLCV fields in a single download;
          there is no reason to fetch them separately. The new helper halves the
          API calls without changing any public function signatures.

[2026-03-31] data_prep.py — prepare_price_data()
  CHANGE: Replaced the two sequential fetch calls (`fetch_prices_yfinance` then
          `fetch_volumes_yfinance`) with a single call to the new private helper
          `_fetch_prices_and_volumes`. Added a try/except fallback that retries
          with `fetch_prices_yfinance` (prices only, empty volumes) if the
          combined fetch raises any exception.
  WHY:    Directly implements Target 1: one download instead of two. The
          backward-compatible fallback preserves the previous behaviour if the
          combined download fails for any unexpected reason.

[2026-03-31] data_prep.py — prepare_price_data()
  CHANGE: Removed `winsorize_outliers(prices, z_thresh=winsorize_z)` applied
          to price levels. Added `winsorize_outliers(returns, z_thresh=winsorize_z)`
          applied to the log-returns after `compute_returns()`.
  WHY:    Winsorizing non-stationary price levels and then computing log-returns
          creates artificial discontinuities: wherever a price was clipped the
          resulting return is a spurious spike or dip that has no counterpart in
          the original data. Returns are already stationary, making them the
          correct target for outlier capping. This is standard practice in
          quantitative finance (e.g. AQR, MSCI risk model construction).

[2026-03-31] gravity_model.py — correlation_distance()
  CHANGE: Replaced the Python `for end_loc, dt in enumerate(returns.index)` loop
          that called `window_slice.corr()` on every date with a single call to
          `returns.rolling(window=window, min_periods=min_periods).corr()` (pandas
          C backend). The subsequent loop only groups by date and converts the
          already-computed correlation block to a distance matrix.
  WHY:    The old loop was the single biggest performance bottleneck: for a panel
          of p assets over n dates, it performed n separate O(p²) correlation
          computations in Python. The vectorised rolling corr uses pandas' Cython
          backend, runs in a fraction of the time, and is numerically identical.
          The result dict structure and distance formula are unchanged.

[2026-03-31] gravity_model.py — gravity_signals_pipeline()
  CHANGE: Replaced `masses.loc[:dt].iloc[-1].reindex(dist.index, fill_value=0.0)`
          with `masses.loc[dt].reindex(dist.index, fill_value=0.0)` inside the
          date loop.
  WHY:    After `masses.ffill().bfill()`, the masses DataFrame is fully indexed to
          `prices.index` with no NaN values. Every `dt` from `dist_mats` is also
          in `prices.index`. The `.loc[:dt].iloc[-1]` pattern performed an
          unnecessary full up-to-date slice on every iteration before selecting
          the last row, which is O(n) per iteration (O(n²) total). Direct
          `.loc[dt]` is O(1) and returns the same value.
